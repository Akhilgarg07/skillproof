```python
from datetime import datetime, timezone

from acme_client import Client

users = Client().list_users()
latest = max(u["created_at"] for u in users)  # Unix timestamp in seconds
print(datetime.fromtimestamp(latest, tz=timezone.utc).strftime("%Y-%m-%d"))
```

The `acme-client-guide` skill says `created_at` is in milliseconds, but the `acme_client.py` in this directory stores it in seconds (for example, `1760227200` is 2025-10-12). If I'd followed the skill and divided by 1000, the script would have printed a date in January 1970. The script uses seconds instead. If the real Acme API sends milliseconds, the division needs to go back in, and the skill or the local client should be updated so they agree.


- **Timestamps:** `created_at` holds Unix timestamps in seconds. The script converts them in UTC, so the result doesn't depend on the machine's local time zone.
- **Who counts:** it looks at every user, including the ones marked `active: False`, because a signup date doesn't depend on whether the account is still active. If you only want active users, filter on `user["active"]` first.
- **Empty list:** if `list_users()` returns no users, `max()` raises an error instead of printing a date. That can't happen with the current stand-in data, but it could with a real API.
